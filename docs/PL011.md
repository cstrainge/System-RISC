# PL011 console on BCM2837

The board's console is the ARM PrimeCell PL011 at `0x3F201000`, driven by the
boot payload and by the resident kernel. This document is the register contract
for both, and the reasoning about whose code it belongs in.

## Why this document exists

The console is the one device whose failure is invisible: a console that does not
work produces no message saying so. It is also the device the firmware may have
already configured, and the device whose clock comes from a block this platform
does not drive. Both facts have to be decided rather than assumed.

## Registers

All access is little-endian, 32-bit except where a narrower width is stated.

| Offset | Name | Access | Meaning |
| --- | --- | --- | --- |
| `0x00` | Data | read/write | Transmit when written; receive when read, with four error flags in the high bits |
| `0x04` | Receive status / error clear | read/write | Reads the error bits of the last received character; writing any value clears them |
| `0x18` | Flags | read-only | FIFO and modem state |
| `0x20` | IrDA low-power counter | read/write | Not used; leave at reset value |
| `0x24` | Integer baud divisor | read/write | Whole part of the divisor |
| `0x28` | Fractional baud divisor | read/write | Six-bit fractional part, in 64ths |
| `0x2C` | Line control | read/write | Word length, parity, stop bits, FIFO enable |
| `0x30` | Control | read/write | Enable, transmit enable, receive enable, loopback, hardware flow control |
| `0x34` | Interrupt FIFO level select | read/write | Trigger levels for the receive and transmit FIFO interrupts |
| `0x38` | Interrupt mask set/clear | read/write | One bit per interrupt source |
| `0x3C` | Raw interrupt status | read-only | Sources as they are |
| `0x40` | Masked interrupt status | read-only | Sources that are both raw and unmasked |
| `0x44` | Interrupt clear | write-only | Write one to clear |
| `0x48` | DMA control | read/write | Not used by the console |

### Identifier

`0xFE0`–`0xFFC` hold the PrimeCell and peripheral identification registers. A
driver may use them to confirm it has a PL011 rather than the mini UART inside
the auxiliary block, whose register layout is entirely different and whose base
address is nearby.

## Flags

Bit 0 clear to send, bit 1 data set ready, bit 2 data carrier detect, bit 3
transmit FIFO busy, bit 4 receive FIFO empty, bit 5 transmit FIFO full, bit 6
receive FIFO full, bit 7 transmit FIFO empty, bit 8 ring indicator.

A character may be written only while bit 5 is clear and read only while bit 4 is
clear. Bit 3 says the transmitter is still shifting out a character, which is
what a console must wait for before powering the UART down; it is not a
precondition for writing.

## Baud arithmetic

The divisor is `UARTCLK / (16 × baud)`, split into an integer part and a
fractional part rounded to the nearest 1/64. For a 48 MHz clock and 115200 baud
the divisor is 26.0416…, so the integer register holds 26 and the fractional
register holds 3.

**Ordering constraint.** The divisor registers and the line control register share
an internal latch: the new divisor takes effect when the line control register is
written. A driver that writes line control first and then the divisor runs at the
previous baud rate until something else writes line control again, which
typically presents as garbled output at exactly one baud rate — the second one
configured — and nothing wrong at the first.

### Where the clock comes from

The UART clock is produced by the clock manager, which the VideoCore firmware
owns. The firmware's configuration therefore decides the rate:

* With the UART enabled for the ARM's use, the firmware fixes the core clock so
  that the UART clock does not change under the guest, and its clock is a
  documented constant of that configuration.
* A configuration that does not enable the UART may leave the core clock scaling
  with demand, in which case any divisor computed once is wrong as soon as the
  clock changes.

A driver must therefore take its rate from one of two places, and the platform
record is where that decision belongs: the rate the board's firmware
configuration produces, or a rate read back from the clock manager. It must not
assume a default, because the failure mode of a wrong assumption is silence.

## Line control

Bits 5:4 select the word length (`11` is 8 bits), bit 3 enables both FIFOs, bit 2
selects two stop bits, bit 1 selects even parity and bit 0 enables parity. The
board's console uses 8 data bits, no parity, one stop bit, FIFOs enabled.

With the FIFOs disabled the receive side effectively holds one character, so an
interrupt-driven reader has one character's worth of slack. With them enabled the
FIFOs are 16 characters deep, and the receive timeout interrupt is what wakes a
reader when fewer than the trigger level have arrived.

## Control

Bit 0 enables the UART, bit 8 the transmitter and bit 9 the receiver. All three
are required for a console that both prints and reads. Bits 14 and 15 enable
hardware flow control, which the board's console does not use.

Enabling the UART while the FIFOs are disabled discards any character in flight;
the safe order is to configure the line and divisor, flush by reading the data
register until the receive FIFO is empty, then enable.

## Interrupts

Mask bit 0 receive, 1 transmit, 2 receive timeout, 3 framing error, 4 parity
error, 5 break error, 6 overrun error. The same bit positions appear in raw,
masked and clear registers.

* Reading the data register is what removes a character from the FIFO; it is also
  what clears a receive or receive-timeout interrupt.
* Writing to the clear register with a bit set clears that source. Clearing a
  receive condition without reading the data leaves the character in the FIFO and
  the condition returns immediately.
* An overrun is reported once, and the character that caused it is lost. A reader
  that only checks the data register never sees it, so a console that must report
  loss has to check the error bits.

## Boot configuration

Three firmware settings decide what the ARM inherits:

* Enabling the UART for the ARM assigns the PL011 to the header pins; without it
  the header carries whichever channel the firmware chose, or nothing.
* Second-stage UART output makes the firmware print its own diagnostics on this
  console before the ARM runs. That output is not ours and must be expected rather
  than treated as corruption.
* The default UART clock is a firmware default, not an SoC constant.

## Driver, resident code, or bootloader?

The console is needed in three places: the boot payload prints its progress, the
resident kernel prints diagnostics before and after drivers load, and an
application may want a terminal. Only the third is a driver's job in the sense the
rest of this tree uses the word.

* **The boot payload keeps its own minimal writer.** A driver cannot exist before
  the services that would load it, and a bootloader that needs a module to print
  its first line can never report a failure to load one. This writer is a
  register-level transmit only; it does not own interrupts or the receive path.
* **The resident kernel owns the console channel** for diagnostics, because it
  must be able to print during a panic, which is exactly when no module service
  is trustworthy.
* **Character I/O for applications is a separate question** and needs its own
  class, because it has to arbitrate between the kernel's diagnostics and an
  application reading the same receive FIFO. Until that class exists, an
  application must not be given raw access to this UART: two readers of one
  receive FIFO lose characters and neither can tell.

## Rules an implementation must satisfy

1. Wait for the transmit FIFO not-full flag before writing a character; never
   assume the last write drained.
2. Program the divisor before the line control register.
3. Enable the UART, transmitter and receiver, and enable the FIFOs before use.
4. Take the clock rate from the platform record or the clock manager, never from
   a remembered default.
5. Drain the receive FIFO by reading, not just by clearing the interrupt.
6. Report overrun, framing and break errors when reading, and make the loss
   visible rather than silent.
7. Never share one receive FIFO between two owners without an arbiter.

## Documented errors in the published register map

Three errors in the family register document bear directly on this device, and
the behaviour described above is the hardware's, not the document's:

* **The base address is printed with a digit missing.** It is `0x3F201000` in the
  ARM view (`0x7E201000` in the VideoCore view), not the shorter value the UART
  section prints.
* **The interrupt clear register's description is copied from the masked-status
  register** for two of its fields, so the document appears to say those fields
  report status. They clear. Writing a one clears the source; this is the register
  the interrupt rules above rely on.
* **The nominal core clock the document quotes for rate calculations (150 MHz) is
  not this board's (250 MHz).** A divisor computed from the document's figure
  produces a baud rate 1.67 times too slow, which is slow enough that a terminal
  shows nothing usable rather than wrong characters.

The transmit and receive paths describe correctly. The FIFO depth, the flag
positions and the divisor arithmetic are as documented.

## What this document does not establish

That the configured baud rate actually appears on a wire, that the firmware's
default clock is what a particular configuration produces, or that the pins are
routed as expected. Those are board facts. The emulator will accept the
configuration whatever it is, so a working console there says only that the
register sequence was well-formed.
