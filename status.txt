System RISC platform-driven build - report
==========================================

State: build and boot verified on this host. No commits made (coordinator
instruction). HEAD is cc8ebfb0 with the rewrite uncommitted in the worktree.

1. What the build is now
------------------------
platforms/<name>.json is the build manifest and tools/xtask is its interpreter.
A platform record states the target, the compiler pin, the memory layout, the
machine and its devices, the storage images and partitions, the bootloader, and
which packages the platform installs. Nothing in that list is restated in Rust
or in .cargo/config.toml.

One command builds and boots:
    cargo xtask build --platform qemu_riscv
The platform name is matched with case and punctuation ignored, so QemuRISC-V,
qemu-riscv and qemu_riscv are one platform, and every output path uses the
canonical spelling qemu_riscv.

3. Platform schema
------------------
Top level: include | name | description | rust_target | std_target |
llvm_profile | profile_requires | memory | virtual_memory | scheduling |
fatal_shutdown | hardware | emulation | storage | install | bootloader.

install is the installed set:
  applications  ordered application packages
  modules       resident System, driver and extension packages
  features      per-package Cargo features
  folders       the guest folder each package group installs into
  exceptions    packages installed somewhere other than their group's folder

Definitions are not install.modules entries. Every definitions/* package is
built from the tree by the `definitions` stage, and the System's own
resources.json names the native-code artifact it embeds, so the installed set
and the embedded set cannot drift apart.

Includes: a record may name one include. Merge rules:
  scalar            replace
  plain array       replace
  object            merge key by key, recursively
  "$append"         extend the array instead of replacing it
  paths             relative to the including record
  missing include   error naming both files
  cycle             error naming the cycle
Example pair (abridged):

riscv_base.json
{
  "name": "riscv_base",
  "rust_target": "riscv64imac-unknown-none-elf",
  "llvm_profile": "rva23u64",
  "profile_requires": ["v", "d", "f", "zba", "zbb", "zbs"],
  "memory": { ... }, "virtual_memory": { ... }, "scheduling": { ... }
}

qemu_riscv.json
{
  "include": "riscv_base.json",
  "name": "qemu_riscv",
  "std_target": "riscv64-unknown-systemrisc.json",
  "install": { "applications": ["mac-finder", ...], "modules": [...],
               "folders": {...}, "exceptions": { "mac-finder": "System Folder" } },
  "storage": { "images": { "system-disk": { ... } } },
  "emulation": { "family": "qemu", "machine": "virt", ... },
  "bootloader": { "package": "bootrom-riscv", ... }
}

arm_virt.json is a second record that reuses the same schema with different
machine data. It is data only: no ARM boot exists, and the report does not claim
one.

4. Adding an application
------------------------
  1. Add the crate under apps/<name> with resources.json (role, binary name).
  2. Add the package name to platforms/<platform>.json install.applications.
     Per-package features go in install.features.
  3. cargo xtask build --platform <platform>.
That is the whole change. The graph read, the compile, packaging, the image and
the boot all follow from the record; no build-tool file is edited.

5. Ninja
--------
xtask generates dist/<platform>/ninja/build.ninja from the record and the
package graph, with rules for definitions, guest, applications, packages,
storage image and boot. Every rule invokes `xtask stage <name>`; each stage
writes dist/<platform>/ninja/stamps/<stage> with restat = 1, digesting the
platform's output tree. A stage that changes nothing reruns its consumers only
if the digest moved.

How ninja is obtained for a first-time user:
  SR_TOOL_NINJA, then PATH, then the per-user cache, then install.
  Windows:  winget install --silent --accept-package-agreements               --accept-source-agreements Ninja-build.Ninja
  Debian-family Linux: sudo apt install ninja-build
  Other Linux: the distribution's own package manager, named for that host
  macOS: brew install ninja
`cargo xtask tools` prints exactly that for the current host and never installs.
`cargo xtask tools --install` performs the install (Windows: winget, else a
pinned checksum-verified download; elsewhere it still only informs).
On this host ninja is not on PATH; resolution finds the copy shipped with Visual
Studio 18 (1.13.2), which is why the build works without an install step.

6. Corrections made after external review
-----------------------------------------
The first draft of this report claimed a working command that did not parse.
Four defects were found by re-reading and re-running, and each is fixed here:

  a. Global flags were only accepted before the command word, so the documented
     `cargo xtask build --platform qemu_riscv` failed with "'build' takes no
     arguments". Flags are now recognised on either side of the command word,
     and `--` still stops the scan so `run -- --platform x` reaches the
     emulator.
  b. `cargo xtask platforms` failed on the ARM record, which still used the
     previous emulation/hardware vocabulary (`hardware.memory` and a disk
     `capacity` on an enum that no longer had one). The record is migrated, and
     the catalogue now names an unloadable record with its error instead of
     letting one stale file hide every other platform.
  c. Nothing pinned the host toolchain: the branch needs nightly, and plain
     `cargo` chose stable and failed in mac-object-table. `rust-toolchain.toml`
     now pins nightly-2026-10-05 with rust-src and rustfmt, and `cargo xtask`
     refuses to build when that file and `platforms/rust/sdk.json` disagree, so
     the pin is a checked copy rather than a second authority.
  d. `boot-check` was a "checking" command: it rebuilt everything into
     build/check/target with the tracing features for eight minutes and then
     failed on the module contract, so it never verified the build that exists.
     It now uses the build's own target directory and features.
  e. `stamps/image` was written but never declared by a graph target. The image
     rule now declares the stamp and the medium together.
  f. The run console was never stored: `run` connected the guest console to the
     host's stdout and nothing else, so no run left a log. It is now copied to
     <platform>/serial.log while the guest runs.

Three further defects surfaced while making (d) work, and each is a real
correctness problem rather than a harness detail:

  g. The boot-check cases booted the platform's own disk no matter what media
     they asked for, because attachments always added the record's disks first.
     A case meaning "no disk" therefore booted a desktop. `Media::Given` now
     replaces the record's attachments for one run; `run` keeps using the
     record's.
  h. The emulator's file console backend buffers, so a reader polling the file
     saw nothing until the process exited: readiness looked like a stall. The
     console is now read from a pipe and written by the host, and the obsolete
     file variant is gone.
  i. The readiness budget was 15 s while a cold boot on a development host takes
     about 19 s to `BOOT_SYSTEM_READY:` and 20 s to `DESKTOP_READY:`. It is now
     60 s, documented as data because a slower board or host changes it. A
     check that fails on a working boot reports the platform as broken.
  j. Two boot cases asserted `CNID=16` for the blessed System Folder. That
     number shifts whenever the volume's contents change, and it is now 17. The
     cases assert that a blessed folder was found, not which catalog number it
     received.

11. Spec conformance after review
--------------------------------
Three deviations were raised against the first commit, and each is now fixed
with the evidence below.

A1, one source of truth for the ISA profile. `.cargo/config.toml` no longer
carries any target rustflags. The guest build receives
`--config target.<triple>.rustflags=[...]` built from `platform.llvm_profile`
and a fixed `relocation-model=pic`, so the record is the only place the
profile is written. Acceptance run: setting `llvm_profile` to `rva22u64` in
`platforms/riscv_base.json` and rebuilding failed with
"compiler does not implement the full rva22u64 profile (rva22u64/v/d/f/zba/
zbb/zbs required)" - the name in the message is the record's value, with no
other file edited. Reverting and rebuilding the guest stage exited 0.

A2, per-package features. The record's `features` map is the shipped set and
is read by one function; the three tracing features are one documented
`DIAGNOSTICS` table keyed by package, feature, environment variable and
whether `cargo xtask check` enables it. `install.rs` states that diagnostics
are never record data and why. Each build prints the resolved feature list for
a package that has any, so what was compiled is visible rather than inferred.

A3, the platform names its compiler. Both records carry
`"toolchain": "rust/sdk.json"`; `sdk.rs` and the workspace resolve the pin
through `platform::compiler_path`, and patch paths resolve beside the pin
rather than from a hardcoded directory. `platform.rs` documents that one
checkout resolves one toolchain per run, because rustup reads
`rust-toolchain.toml` before the build tool starts, and that `cargo xtask`
refuses to build when the pin and the record disagree. Verified: a record
naming `rust/does-not-exist.json` fails at `sdk prepare` with that path.

12. Review round three: findings and fixes
----------------------------------------
B1. `crates.rs` no longer fills a missing package name, manifest path or
directory with `unwrap_or_default()` / `"."`. A metadata entry without an
identity is skipped the same way one without an id already was, and a package
the tree cannot place is an error naming the package instead of being
classified as host code.

B2. The SDK compiler diagnostic had 72 spaces where a line join had gone
wrong; it now reads "the SDK compiler requires SR_SDK_SYSROOT to name its
private sysroot".

B3. `altered_system` took a `directory` it never used and silenced the warning
with `let _ = directory;`. The parameter is gone and both callers updated.

B4. The console recorder ignored `write_all`/`flush` failures, so a truncated
log would be reported as the guest never reaching `DESKTOP_READY` - blaming
the guest for the recorder, on the file the acceptance criterion rests on. A
read or write failure is now recorded and returned as "the console log for
<case> was not recorded: <cause>". The in-memory copy is still what readiness
is judged from, so the failure is reported rather than converted into a
different one.

B5. The `tools.rs` module doc listed four search steps while the code had
five; the missing one - this host's own install locations - is why ninja
resolves here at all. The doc and the printed summary now list all five.

B6. `SR_EMULATOR` was a second override name for QEMU that no other program
had, and the spec never defines. It is gone; `SR_TOOL_QEMU_SYSTEM_RISCV64`
is the one spelling. Verified: exporting `SR_EMULATOR` to a path that does not
exist no longer changes what `cargo xtask tools` reports.

B7. QEMU was probed only under `Program Files`. The per-user locations winget
and manual archives use (`%LOCALAPPDATA%\Programs\qemu`,
`%LOCALAPPDATA%\qemu`, `%USERPROFILE%\qemu`) are probed too.

Python suite. The branch went from 13 failures / 4 errors to 8 failures / 1
error; `main` is 9 failures / 1 error, so the seven breakages this branch had
introduced are fixed and one pre-existing failure is now correct. Four causes,
all of them consequences of the moved build root rather than of the scripts'
logic:

  - `sr_paths.host_dir()` returned a fixed `<checkout>/target` and ignored
    `CARGO_TARGET_DIR`, so a caller that selected a build root got host tools
    from somewhere else. It honours the variable now.
  - `riscv_vm.py` counted `parents[2]` to find the enclosing workspace, which
    was true only for the old one-level layout. It now walks up until the
    directory holding the recorded host QEMU appears, and keeps the checkout
    as its own root for everything the build produces.
  - `system7_vm.py` ran `cargo xtask image --build-dir` and derived the media
    root from the build root. It runs `cargo xtask build`, and check mode gets
    its own `SR_DIST` so a check never opens the desktop's images.
  - Four tests asserted the old roots (`build/system7/check/dist`,
    `<build>/host`, `<build>/dist`). They now assert the roots the build
    actually produces: `<checkout>/target` (or `CARGO_TARGET_DIR`),
    `<checkout>/build/check/dist/<platform>`, `<checkout>/dist/<platform>`.
    The assertions are as strict as before; only the layout they name changed,
    which is the intended and documented move.

Three of the four VM tests the coordinator listed as failing only fail while a
stray QEMU holds port 4447. One from an earlier session was found listening
there and stopped; with the port free they pass.

Also fixed while here: registering the SDK key as a directory name pushed
object paths past Windows' 260-character limit, and the host linker reported
"cannot open file" for an rlib that exists. The key is now a marker file that
clears stale application artifacts, which is what the directory name was for,
without lengthening the paths.

`cargo xtask doc` also emitted `rustdoc::invalid_html_tags` for
`/Volumes/<unique mounted name>/...`, which rustdoc reads as a tag; the path is
in backticks now.

Pipes facility: collision audit, feasibility report and specification

State: audit and specification only. No implementation and no source change

1. Gate zero: the Toolbox surface the facility must not step on
----------------------------------------------------------------
Trap allocation. Native service numbers are hand-allocated in
crates/mac-abi/src/traps.rs and dispatched by one match in
system/src/machine/traps.rs (dispatch), after size and pointer validation in
system/src/machine/traps/user.rs plus the wire table in user/wire.rs. The
block 0x10000..0x1002e is fully occupied with no gaps:

  10000 LOG        1000f MAPPING          1001f CRASH
  10001 WINDOW     10010 RESOURCE         10020 STANDARD_FILE
  10002 DRAW       10011 ICON             10021 SCROLL_BOX
  10003 NEXT_EVENT 10012 FILE             10022 DRAG
  10004 DEFINITION 10013 CONTROL          10023 POSITIONED_EVENT
  10005 CLASSIC    10014 MEMORY           10024 INSPECTION
  10006 GEOMETRY   10015 IMAGE            10025 THEME
  10007 SURFACE    10016 MENU             10026 DEFINITION_PANIC
  10008 QUICKDRAW  10017 DIALOG           10027 POWER
  10009 FONT       10018 CLOCK            10028 APPLICATION_HEAP
  1000a REGION     10019 SCRAP            10029 CPU_INFO
  1000b COPY_BITS  1001a EVENTS           1002a NATIVE_THREAD
  1000c WORLD      1001b TEXTEDIT         1002b TLS
  1000d PICTURE    1001c PROCESS          1002c ADDRESS_WAIT
  1000e CURSOR     1001d WAIT_EVENT       1002d ENTROPY
                   1001e MONOTONIC_CLOCK  1002e USER_CALLBACK

Bit 0x20000 is a modifier (Pascal/Mac Roman text variant), not an allocation,
so it consumes no number. The supervisor scheduler's MSRV entry is a separate
custom instruction encoding (0x4d535256 in a different encoding space).
Allocated: 0x1002f = PIPES. Operation selectors 0..6 live inside the pipes call
and share no namespace with any other service.

Status values 0..-20 are taken (OK through INVALID_NAME). Allocated: -21
WOULD_BLOCK, -22 BROKEN_PIPE.

Module/interface class ids are open four-byte values owned by the interface
crate and compared by value; there is no central assignment. In use: VBYT,
VDEV, ENTR, FORK, FSYS, HDIR, MLIF, MPRE, POWR, SCHD, SCTL, SCEX, VIDO; buses
BUS!, VIRT, PCI!, VMMI; fixtures TEST/PCTL/TIME/NETW. Allocated: PIPE; it
appears in no class position.

Object/lifetime namespaces are registered centrally (mac-object-table registry
through system/src/toolbox/handles.rs). The older fixed Kind table is closed;
new managers use KindCode pools. Allocated: PIPE (endpoints) and PPST
(runtime state), following the endpoint/state pair shape. Neither code appears
anywhere in the tree.

File type and creator: PIPE/PIPE appear in no FinderInfo position, no resource
and not in crates/mac-file-types/default.json. Resource type PIPE: unused, and
the facility allocates no resource type at all. The repeated four bytes are
deliberate across three identifier spaces that are never compared with each
other.

Operation names. read/write/open/close already exist as inherent methods on
distinct handle types in distinct modules (toolbox-files OpenFile, toolbox-
memory, toolbox-resources, toolbox-crashes, ...). The classic File Manager's
Open/Read/Write/Close are not implemented in this build: the classic
dispatcher serves drag, rect/point geometry, text/fonts, cursors, events and
TickCount only. So no classic number or selector is shadowed, and pipe methods
are disambiguated by module and receiver type rather than renamed.

One real coupling found: crates/mac-toolbox/tests/file_icons.rs
(native_system_icon_reservation_preserves_classic_ids_and_rejects_import_
collisions) treats -30031..=-30000 as a reserved native icon block and allows
only DRIVERS_FOLDER (-30000) and DRIVER (-30001) inside it. New folder and
document icon families at -30002/-30003 must extend that allowlist, or the
canonical suite fails. That is a policy-allowlist update, not a harness
accommodation.

2. Sub-volume provider mounts and merged listings: neither exists
-------------------------------------------------------------------
system/src/toolbox/files/provider/ models a provider as a whole volume.
reserve_provider_mount returns a volume id; Mounted holds provider, source and
an optional VolumeInfo; volume_info is built from the fs::Mount root descriptor
(name, dates, FinderInfo, capacity, filesystem code). There is no mount point
below a volume root. Enumeration and lookup are either/or, not merged:
provider/runtime.rs gates on read_provider(volume) and then dispatches to
either the resident HFS scanner or the provider job. A directory read returns
one source's children only.

Two implementation shapes, with the provider finding stated first:

  (a) True sub-volume provider mount. Add a mount point to Mounted, project
      provider entries into the real directory's catalogue, allocate a shared
      synthetic CNID space both sources agree on, merge the cursor across two
      revisions, and route lookup/path/open by node. Plus a pipes provider
      module and its admission/acknowledgement path. Rough estimate 1,800-2,500
      lines resident, excluding the pipes facility itself.

  (b) File Manager enumeration directly from the resident name registry.
      Named pipes are resident System state, not an independently owned storage
      format, so the File Manager merges its own catalog children with the
      registry's entries for the one registered folder CNID: merged cursor with
      one revision, lookup fallback, synthetic ids never reused within a boot,
      mutations refused. Rough estimate 600-1,000 lines resident.

The specification (docs/PIPES.md, section 9.5) requires (b) and records why:
(b) adds no driver boundary around state that never leaves the System, and a
general sub-volume mount is a separate, larger change that nothing in the pipe
contract depends on. This is the one design point that departs from the
settled wording ("a virtual provider mounts at that path") and is the item for
review.

3. Where the stubbed pipes actually are
----------------------------------------
There are no pipe stubs in system/, crates/, toolbox/, apps/, drivers/ or
extensions/. A case-insensitive search for "pipe" over those trees matches
nothing in Rust sources; the only implementation-shaped code in the repository
is the platform standard-library null stream profile:

  platforms/rust/library/std/src/sys/stdio/systemrisc.rs

stdin returns 0 forever (permanent end of stream); stdout and stderr accept
every byte and report a successful flush. It states in its own header that it
is not a Terminal/session endpoint or a pipe implementation. Stderr is a type
alias of the discarding stdout. There is no sys/pipe module in the vendored
std, no PAL pipe call, and no resident stdio endpoint table: the loader
attaches the SystemServices table, which carries no stream endpoints.

So docs/RUST-STD.md:239 ("replacing kernel stubs through the service
boundary") and 434-437 ("replaces resident stubs", "a parallel full kernel
pipe implementation") describe stubs that do not exist on this tree. The
honest statement is: the GUI profile has intentionally null standard streams,
and no anonymous-pipe stub exists anywhere.

Consequence for acceptance: GUI launch keeps the null streams unchanged, as
directed. The launch path installs no endpoints, so there is nothing to convert
and nothing to break. In v1 the facility's only caller is an application that
asks for pipes explicitly; the named first caller is the NeoPixel extension.

4. Proposed API surface
------------------------
Trap PIPES = 0x1002f. One call struct with operation, endpoint handle, capacity,
blocking flag, buffer pointer and length, transferred count, two out handles and
a bounded inline name. Operations: create, create_named, connect, read, write,
set_blocking, close. New SDK crate toolbox-pipes behind System::pipes(), with
PipeReader and PipeWriter handle types (Drop closes), read/write/set_blocking/
close as methods.

Blocking uses the existing suspended-request path (RequestResult/RequestAction,
per-thread pending storage, a new Wait variant, wake::request), so a blocked
caller parks and is woken by ring state change or peer close. Non-preemptible
frames are refused with WRONG_THREAD rather than spinning.

Semantics fixed in the spec: 512-byte all-or-nothing writes and no implied
record size; partial transfers for larger writes and for reads; capacity fixed
at creation (512..65536, at most 64 pipes); distinct end-of-stream,
would-block and broken-pipe outcomes; name removed when the last handle closes;
no authority in v1.

5. What was produced
---------------------
docs/PIPES.md: code-free contract, 14 sections, including the numbering and
register tables above, the folder merge and item identity, opening as connect,
the icon plan (-30002 folder placeholder copied from the standard folder
family, -30003 document family plus a PIPE-signature bundle), the launch-path
table that keeps the stubs, and the deferred list.

Validation: documentation only. No build or check was run for this entry, and
no guest acceptance is claimed. Boot check remains at its last recorded state
(17/17 on the merged tree) until an implementation tip is built.

-------

any code. Implementation order after that: pipe core and handles, blocking
integration, File Manager merge, folder creation, Finder open, icons.

Findings:

- CLAP appears in the tree only as prose (docs/TERMINAL.md, RUST-STD.md,
  CORE-TOOLBOX-ROADMAP.md, EXTENSION-TRAITS-DESIGN.md). No code, resource or

- create is already an ordinary application operation in the specified surface.
  There is no System-only creation path and no privileged caller, so a Terminal
  can create the three pipes and hold one end of each as specified.
- The launch interface cannot carry pre-made handles. ProcessCall identifies a
  target only by volume and CNID and has no attachment, endpoint or handle
  field. The services table an application receives at entry is one System-wide
  immutable 16-byte record (version, size, trap gate, capability bits) with no
  per-application attachment record. Standard streams come from the
  application's own standard-library profile. A Terminal would additionally
  need: a launch call accepting three pipe handles; a defined ownership
  transfer of those handles to the child at commit, with the parent's copies
  invalidated (and no transfer on refusal); and a child-side way to read its
  endpoints so the std profile can bind real streams. This facility supplies
  the pipes and the last-close consequences only. The gap is recorded in the
  spec rather than designed around; no launch ABI was changed.

  first: a provider exists because a volume's contents come from somewhere

  exist for nobody. The estimate stands, but is presented as supporting rather
  than deciding.
- The icon reservation allowlist in
  crates/mac-toolbox/tests/file_icons.rs will be extended for -30002/-30003 as
  a deliberate policy change, with the reason in the commit.
- Process exit with a named pipe open is stated explicitly in section 8: every
  handle closes, last close destroys the pipe and removes the name, and a
